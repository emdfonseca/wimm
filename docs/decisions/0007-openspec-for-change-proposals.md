# 0007 · OpenSpec for change proposals

## Status

Accepted

## Context

Decisions are recorded in `docs/decisions/` after the fact. Nothing in the repo
holds the step before a decision: the proposal, the spec delta it implies, and
the task list that carries it to done. That work currently lives in chat
transcripts, which are not reviewable and do not survive the session.

OpenSpec (`@fission-ai/openspec`) is a spec-driven workflow: a change proposal
and its spec deltas live as markdown under `openspec/changes/`, an agent works
against them, and `openspec archive` folds the delta into `openspec/specs/` when
the change lands. The artifacts are plain files, so they review as diffs.

It is a Node CLI and is not packaged in nixpkgs, so devbox cannot own it the way
it owns Go, pnpm and buf.

## Decision

OpenSpec holds change proposals and living specs. ADRs keep their role: a
decision record says what was chosen and why, a proposal says what is about to
be built. They are not substitutes.

The CLI is pinned in `bin/openspec`, a shim that execs `pnpm dlx` at an exact
version. devbox prepends `$DEVBOX_PROJECT_ROOT/bin` to `PATH`, so inside the
project shell a bare `openspec` is the pinned one.

The pin has to live on `PATH` rather than only in a just recipe. OpenSpec
generates its own instruction files — six `opsx` commands and six `openspec-*`
skills — and they invoke a bare `openspec` around a hundred times. A recipe
would leave every one of those calls resolving to whatever the machine happens
to have installed globally.

`just openspec <command>` delegates to the same shim, so the version is stated
once. There is no root `package.json`: a single dev CLI does not justify
introducing an npm manifest to a repo whose one Node package has no
dependencies.

Claude Code is the only configured tool integration.

## Consequences

- The version moves in one line of the justfile, and the move is a reviewable
  diff. `pnpm dlx` resolves against its own store, so a run needs network the
  first time a version is seen on a machine.
- There is no lockfile for this dependency. The pin is exact, and the registry
  is the trust boundary — the same one pnpm already carries.
- `openspec/specs/` and `openspec/changes/` are tracked. The archive is history
  that a reader needs, unlike the git log, because a spec delta explains what a
  capability is supposed to do.
- OpenSpec installs its own agent instructions under `.claude/skills/openspec-*`
  and `.claude/commands/`. Those are generated by `openspec init`; regenerate
  them rather than editing them. The `PATH` shim is what makes that possible —
  the pin holds without touching a generated file.
- The shim is only on `PATH` inside the devbox shell. A bare `openspec` typed in
  a plain terminal still finds a global install, if one exists, at whatever
  version that is.
- `just check` does not run OpenSpec validation. CI has no opinion on proposal
  quality, and a half-written proposal must not fail a build.
